# ADR-004 Payments отдельно от Billing

← [[Edvantix]]

**Статус:** принято · 2026-08-09

## Контекст

В системе два независимых денежных потока:

1. **Школа → Edvantix** — подписка на платформу. Уже реализовано в [[Billing]]:
   `BillingPlan`, `Subscription`, `Invoice`, `InvoiceLineItem`, `UsageSnapshot`, PDF.
2. **Ученик → школа** — оплата обучения. Требование: «только выставление счёта +
   подтверждение».

Варианты:

1. Новый модуль `Payments`, `Billing` остаётся SaaS-биллингом.
2. Расширить `Billing` на оба сценария.
3. Удалить `Billing`, оставить только `Payments`.

## Решение

**Вариант 1: отдельный модуль `Payments` (порядок 630).** `Billing` не трогаем по существу.

Вариант 3 отпадает автоматически из [[ADR-001 Школа как тенант]]: SaaS-подписка нужна.

## Обоснование

Это **разные ограниченные контексты**, совпадающие только словом «счёт»:

| | Billing | Payments |
|---|---|---|
| Плательщик | школа (тенант) | ученик или представитель |
| Получатель | Edvantix | школа |
| Кто выставляет | автоматически по подписке | менеджер, вручную или пакетно |
| Основание | тарифный план и период | тариф, посещения, зачисление |
| Подтверждение | платёжный провайдер или оператор | менеджер вручную |
| Изоляция | глобальный (кросс-тенантный) | строго тенантный |
| Права | `Platform.*`, root-уровень | права школы |
| Видимость | SuperAdmin + админ школы | менеджеры, ученик, представитель |
| Жизненный цикл | привязан к подписке | привязан к учебному периоду |

Слияние потребовало бы дискриминатора на каждой сущности и ветвлений почти в каждом
обработчике. Худшее последствие — риск ошибки видимости: счёт школы показан ученику или
наоборот. При разделении по модулям это исключено механикой изоляции.

Общее — только рендеринг PDF. Решается переиспользованием интерфейса
`IInvoicePdfRenderer` без слияния модулей.

## Решение по платёжному шлюзу

**Эквайринга нет.** Требование сформулировано явно: выставление счёта + подтверждение.
Система фиксирует обязательство и факт его закрытия человеком; деньги идут мимо платформы.

Прямые следствия, заложенные в модель [[Payments]]:

- `PaymentConfirmation` — утверждение менеджера, ничем не проверяемое. Поэтому:
  - записи **неудаляемы**;
  - каждая пишется в [[Auditing]] с автором и временем;
  - отмена — **сторнирующая запись** (`ReversesId`), а не редактирование;
  - право `StudentPayments.Confirm` — самое чувствительное в системе,
    `Revoke` вынесено отдельно на уровень `SchoolAdmin`.
- Статус счёта выводится из сумм подтверждений, а не задаётся вручную.

## Последствия

**Положительные**

- Два контура денег не пересекаются ни в коде, ни в UI
- Утечка «счёт школы виден ученику» невозможна
- `Billing` остаётся стабильным, `Payments` развивается свободно
- Эквайринг позже добавляется в `Payments`, не задевая `Billing`

**Отрицательные / принимаемые**

- Два похожих набора сущностей — дублирование кода PDF, нумерации, статусов.
  Осознанная цена за разделение контекстов
- В UI нужно чётко разводить: «Подписка» против «Счета учеников».
  Разные разделы меню, разная терминология
- При код-ревью следить, чтобы не смешивали

**Требуемое от Multitenancy**

Валюта школы для Payments — в `TenantSettings`, не в `AppTenantInfo` (защищённый каталог).
