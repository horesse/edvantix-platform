# ADR-003 People как отдельный модуль

← [[Edvantix]]

**Статус:** принято · 2026-08-09

## Контекст

Нужны ученики, преподаватели, представители и менеджеры. В [[Identity]] уже есть `FshUser`
с ролями, группами доступа, сессиями и политикой паролей.

Варианты:

1. Отдельный модуль `People` с профилями, опционально связанными с `FshUser`.
2. Всё через `FshUser` + роли, профильные поля в Identity.
3. `People` полностью автономен, Identity занимается только аутентификацией.

## Решение

**Вариант 1 (по сути совпадающий с вариантом 3):** модуль `People` с сущностями
`Student`, `Teacher`, `Guardian`. Связь с учётной записью — **опциональное** поле
`UserId`. Identity не знает про предметные роли и профили.

Менеджер отдельной сущностью **не моделируется** — это роль пользователя.

## Обоснование

**Ученику не нужен логин.** Ребёнку 8 лет учётная запись не заводится: расписание смотрит
представитель, счета приходят ему же. При варианте 2 пришлось бы создавать фиктивные
аккаунты с выдуманными адресами почты, ломая инварианты Identity (уникальный e-mail,
подтверждение адреса, политика паролей, сброс).

**У ученика есть данные, которых нет у пользователя:** дата рождения, источник заявки,
ответственный менеджер, статус в воронке, представители, внутренние заметки. Складывать
это в `FshUser` — раздувать модуль, общий для всех модулей проекта.

**Один человек может быть в нескольких ролях.** Преподаватель, чей ребёнок учится в этой
же школе, — это `Teacher` и `Guardian` с одним `UserId`. При варианте 2 потребовались бы
взаимоисключающие наборы полей на одном пользователе.

**Identity — правило 4 из `AGENTS.md` по духу:** широкий радиус поражения. Чем меньше
предметной специфики в нём, тем безопаснее.

Менеджер — исключение в другую сторону: он **всегда** пользователь системы (иначе не смог
бы работать), и профиля сверх `FshUser` ему не нужно. Заводить `Manager` в People значит
создавать сущность, дублирующую пользователя один в один.

## Последствия

**Положительные**

- Ученик существует без учётной записи; логин добавляется позже без миграции данных
- Identity остаётся тонким
- Естественное совмещение ролей одним человеком
- Предметные поля живут в предметном модуле

**Отрицательные / принимаемые**

- Двойной справочник: пользователи и люди. UI должен ясно показывать связь и её отсутствие
- Нужен `IPeopleScopeResolver` для ответа «кто этот пользователь в предметной области» —
  иначе row-level проверки расползутся по обработчикам ([[Модель прав доступа]])
- Возможно расхождение данных: e-mail поменяли в профиле, но не в учётной записи.
  **Смягчение:** контакты — источник правды в People; в Identity e-mail только для входа

**Следствия для реализации**

- `Student.UserId`, `Teacher.UserId`, `Guardian.UserId` — nullable
- Эндпоинт «привязать учётную запись» на каждой сущности
- `GET /people/me/scope` — для фронтенда
- Кэш `PeopleScope` в Redis с инвалидацией по событиям People
