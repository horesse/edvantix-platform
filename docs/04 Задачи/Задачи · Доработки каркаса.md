> живущая в модуле, а не в BuildingBlocks.

### Спецификация `TenantSettings`

> ✅ Реализовано. Всё скопировано с `TenantTheme` — он решает ровно ту же задачу
> «данные на тенант, живущие в модуле».

| Что          | Как                                                                                                                                          | Образец в коде                                    |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| Сущность     | `Modules.Multitenancy/Domain/TenantSettings.cs`, `BaseEntity<Guid>`, `IHasTenant`, `IAuditableEntity`                                        | `Domain/TenantTheme.cs`                           |
| DbContext    | `DbSet<TenantSettings>` в `TenantDbContext`                                                                                                  | там же `TenantThemes`                             |
| Конфигурация | `ToTable("TenantSettings", MultitenancyConstants.Schema)`, **уникальный индекс по `TenantId`**, `TenantId` — `HasMaxLength(64).IsRequired()` | `Data/Configurations/TenantThemeConfiguration.cs` |
| Сервис       | `ITenantSettingsService` в Contracts, метод `GetCurrentAsync(ct)` — текущий тенант резолвится внутри                                         | `ITenantThemeService.GetCurrentTenantThemeAsync`  |
| Кэш          | **`HybridCache`**, а не самодельный Redis: `HybridCacheEntryOptions` + теги `CacheKeys.Tags.Tenant(tenantId)`, локальная экспирация ~2 мин   | `Services/TenantThemeService.cs`                  |
| Инвалидация  | по тегу тенанта при обновлении настроек                                                                                                      | там же                                            |

> [!important] `TenantDbContext` — глобальный реестр, а не изолированный контекст
> Он наследует `EFCoreStoreDbContext<AppTenantInfo>`, автоматической фильтрации по
> тенанту в нём нет. Поэтому `TenantId` — **явная колонка с уникальным индексом**,
> ровно как у `TenantTheme`. Не пытайтесь опираться на `BaseDbContext`.

### Решения, принятые до кода

| Вопрос                          | Решение                                                                                                   |
| ------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Часовой пояс по умолчанию       | `UTC`                                                                                                     |
| Валюта по умолчанию             | `USD`                                                                                                     |
| Право на правку                 | новое `SchoolSettings.Manage` (не `Tenants.Update` — тот операторский/root)                               |
| Право на чтение                 | `SchoolSettings.View`, `IsBasic: true` — часовой пояс и валюта нужны фронтенду на каждом экране           |
| Задаются ли при создании школы  | да — `CreateTenantCommand.TimeZoneId`/`Currency` (необязательные, дефолт UTC/USD)                         |
| Нужны ли настройки root-тенанту | да, создаются со значениями по умолчанию (`Edvantix.DbMigrator/Program.cs`, шаг сидирования root-тенанта) |

> [!note] Ещё не сделано
> Роль `SchoolAdmin` теперь засеяна (раздел [[#Identity]] ниже), но её бандл —
> ровно тот же «все не-root права», что и у `Admin` (осознанное решение, не
> временный пробел — см. таблицу решений в разделе Identity), поэтому
> `SchoolSettings.Manage` по-прежнему держат обе роли, не только `SchoolAdmin`.
> Ограничивать `Admin` не планируется: это страховочная роль фреймворка,
> `SchoolAdmin` — редактируемая школой. Правка UI «Tenant» → «Школа»
> ([[Задачи · Frontend]]) не сделана — это отдельная задача.

## Identity

Справочник: [[Identity]]

> [!note] В отличие от `TenantSettings`, здесь без BuildingBlocks
> `RoleConstants.DefaultRoles` (`src/BuildingBlocks/Shared/Identity/RoleConstants.cs`)
> — защищённый файл, но трогать его не нужно: там только `Admin`/`Basic`, и это
> должно остаться так же (см. решение ниже). `PermissionConstants.Admin` уже
> вычисляется как «все не-root права» (`_all.Where(p => !p.IsRoot)`) — школьные
> роли строятся LINQ-фильтрами над существующим реестром, целиком внутри
> `Modules.Identity`.

### Спецификация «Сид ролей школы»

> ✅ Реализовано.

| Что                                             | Как                                                                                                                                                                                                                                                                                                                                    | Образец в коде                                                                                            |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Роли — обычные, не системные                    | **Не** добавлять в `RoleConstants.DefaultRoles`. Обычный `FshRole`, создаётся так же, как роли пользователя через UI                                                                                                                                                                                                                   | `RoleService.CreateOrUpdateRoleAsync` (ветка `role = new FshRole(...)`)                                   |
| Имена ролей                                     | Константы в `Modules.Identity.Contracts` (не `internal`) — Multitenancy уже ссылается на роль школы в своих доках, значит имя может понадобиться другому модулю                                                                                                                                                                        | новый файл, аналогов пока нет — `Group`/`GroupRole` имена сидятся как локальные литералы, это не подходит |
| `SchoolAdmin` — набор прав                      | = `PermissionConstants.Admin` **без изменений** (тот же список, что получает `Admin`). Никакой отдельной сборки не нужно                                                                                                                                                                                                               | `RolePermissionSyncer.SyncAsync`, ветка `adminPermissions`                                                |
| `Manager` — набор прав                          | `PermissionConstants.Admin` **минус** не-`View` действия ресурсов `Identity` (`Users`, `UserRoles`, `Roles`, `RoleClaims`, `Sessions`, `Groups`, `Impersonation`) **плюс** `Users.Invite` (см. ниже)                                                                                                                                   | новый метод в `Modules.Identity`, фильтр по `Resource`                                                    |
| `Teacher` / `Student` / `Guardian` — набор прав | Конвенция: `p.Action == "ViewOwn"` по всему каталогу **плюс** короткий список исключений из таблицы в [[Модель прав доступа]] (`Attendance.Mark`, `LessonMaterials.View`, `Sessions.View` и т.п.)                                                                                                                                      | там же                                                                                                    |
| Точка первого сидирования                       | `IdentityDbInitializer.SeedRolesAsync` — добавить пять ролей в цикл, пропускать на root-тенанте (`tenantId != MultitenancyConstants.Root.Id`)                                                                                                                                                                                          | существующий цикл по `RoleConstants.DefaultRoles`                                                         |
| Точка донасыщения                               | `RolePermissionSyncer.SyncAsync` — те же пять ролей, той же логикой фильтров. **Обязательно**, не опционально: [[People]], [[Curriculum]], [[StudyGroups]], [[Scheduling]], [[Payments]] ещё не реализованы, их права появятся в реестре позже релиза этой задачи — без периодической синхронизации роли останутся с частичным набором | тот же класс, `SyncRoleAsync` уже идемпотентен                                                            |

> [!important] Почему фильтром, а не явным списком имён прав
> Явный список (`"Permissions.Students.View"`, `"Permissions.Courses.View"`, …)
> надо расширять вручную при каждом новом модуле и до появления People/Curriculum/
> StudyGroups/Scheduling/Payments будет просто пустым. Фильтр по `Action`/`Resource`
> над `PermissionConstants.All` подхватывает новые права сам, как только модуль
> зарегистрирует их через `PermissionConstants.Register(...)` — та же идея, что уже
> работает для `Admin` и `Basic`.

> [!warning] Гварды на «последнего админа» не переносим
> `UserRoleService.EnsureMinimumAdminCountAsync` жёстко завязан на
> `RoleConstants.Admin` — и должен таким остаться: это гарантия последнего
> доступа для восстановления. `SchoolAdmin` — обычная нессистемная роль, школа
> может её редактировать и даже удалить (как любую свою роль); `Admin` продолжает
> существовать на каждом тенанте как страховочный аккаунт. Отдельный гвард
> «последний SchoolAdmin» — не делать в этой итерации, роль ничем не отличается
> от прочих пользовательских ролей.

### Спецификация «Приглашение по e-mail»

> [!note] Мягкая зависимость от [[People]]
> «Менеджер отправляет ссылку представителю» подразумевает представителя как
> запись [[People]] (`Guardian`), которого модуль ещё не существует. Механику
> приглашения (создать пользователя → отправить письмо → принять → задать
> пароль) делаем независимо от People; привязку приглашённого пользователя к
> `Guardian`/`Student` через `LinkStudentUserCommand`-подобный вызов — отдельным
> шагом, когда People появится.

| Что | Как | Образец в коде |
|---|---|---|
| Не новая сущность токена | Переиспользовать `UserManager.GeneratePasswordResetTokenAsync` — уже с TTL (`DataProtectionTokenProviderOptions`) и одноразовый по факту (инвалидируется сменой security stamp) | механизм уже используется в `ForgotPasswordCommand`/`ResetPasswordCommand` |
| Новая команда | `InviteUserCommand` (email, ФИО, роль) — создаёт `FshUser` со случайным неиспользуемым паролем и `EmailConfirmed = false`, затем сразу генерирует reset-токен и письмо | `RegisterUserCommand` как основа состава полей, но без `Password`/`ConfirmPassword` |
| Приём приглашения | Существующий `ResetPasswordCommand` (email + токен + новый пароль). Дополнительно — проставлять `EmailConfirmed = true` при успешном приёме приглашения (получение письма на закрытый ящик уже подтверждает адрес) | `ResetPasswordCommand` handler |
| Право на отправку | Новое `IdentityPermissions.Users.Invite`, отдельное от `Users.Create` | по таблице [[Модель прав доступа]] `Manager` не имеет `Users.*`, кроме этого исключения — приглашать нужно, полный доступ к пользователям — нет |
| Письмо | Шаблон через `BuildingBlocks/Mailing` — та же проверка механизма подстановки, что уже стоит в бэклоге [[Notifications]] («Шаблоны сообщений с подстановкой»); не дублировать исследование | `ForgotPasswordCommand` уже шлёт письмо тем же каналом |
| Самостоятельная регистрация | `/self-register` не удаляем и не трогаем backend — просто не вызываем из dashboard UI. Инвайт становится единственным путём получить доступ представителю/ученику на практике | `SelfRegisterUserEndpoint` (анонимный, уже рейт-лимитирован) |
